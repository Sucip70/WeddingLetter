# Template artwork

WeddingLetter stores static artistic layers as versioned data, while gates, particles, masks, icons, photo-frame primitives, and interactive animation remain application code. One generic renderer can therefore serve any number of templates without a React component per design.

## Manifest v1

The validated manifest lives at `layoutSchema.artwork` and is copied unchanged into `Invitation.layout` when an order is created. It contains:

- `schemaVersion: 1`, `designId`, and positive `artworkVersion`;
- optional slots for cover/page/section backgrounds, cover foreground, top/bottom/four-corner decoration, divider, photo frame, texture, thumbnail, and gate background/foreground;
- `default`, `mobile`, and `desktop` sources per slot, each with trusted URL, immutable storage key, MIME type, dimensions, and byte size;
- constrained presentation enums/numbers for fit, position, opacity, scale, motion, layer order, and photo/ornament-cover visibility;
- safe fallback identifiers for the existing ornament, cover-effect, and particle systems.

Database values never contain CSS strings. Invalid or old artwork data is ignored by normalization, so templates and snapshots without artwork continue through the existing motif renderer.

## Object naming and cache policy

Published objects use:

```text
templates/{design-id}/v{version}/{generated-filename}.webp
```

The filename is generated by the API, not copied from the upload. A published version cannot accept more uploads or be overwritten. Confirmed artwork is served with `Cache-Control: public, max-age=31536000, immutable`. A new visual revision always creates `v{n+1}`.

The four original seasonal packages are application-owned compatibility assets under `apps/web/public/themes/seasonal`. Migration `20261012180000_template_artwork` snapshots their v1 manifests without overwriting an existing `layoutSchema.artwork`. All newly published artwork uses storage.

## Artist → administrator workflow

1. The artist supplies WebP (preferred), PNG master, or AVIF for an opaque background, plus a small manifest/recommendation describing slots and presentation. Do not supply SVG uploads.
2. Open **Admin → Templates → template**, then **Artwork versi immutable**.
3. Create a version. Assign each file to a slot and optional mobile/desktop variant.
4. The browser uploads directly through the existing signed R2/local-storage URL. Confirmation reads the object server-side, verifies the actual decoded type and 16–12000 px / 40 MP / 12 MB limits, applies EXIF orientation, strips metadata, preserves alpha, and writes optimized WebP.
5. Choose safe fit/position/motion/visibility values and preview the draft in the existing phone preview.
6. Publish. The API writes the immutable manifest, activates it on the template, and retains every prior version. Existing invitation snapshots keep their old manifest.

There is intentionally no artwork/version deletion endpoint. This guarantees that assets referenced by JSON invitation snapshots cannot be removed. Lifecycle tooling may add garbage collection only after proving no snapshot references a version.

## R2 and local development

No artwork-specific storage client exists. Artwork uses `StorageService`, `R2Driver`, and the same R2 variables documented in the root README. Configure bucket CORS for signed browser `PUT` requests from `WEB_BASE_URL`. `R2_PUBLIC_URL` should be a CDN/custom-domain HTTPS origin whose cache honors the immutable header.

Without complete R2 credentials and outside production, the existing local driver stores the same nested keys beneath `UPLOAD_DIR` (default `apps/api/uploads`) and serves them from `/media/local/...`. No new environment variables are required.

## Adding a new artwork template

Create or select the template in the builder, upload and publish an artwork version, then publish the template. No React edit is necessary. For programmatic seed data, provide a value accepted by `artworkManifestSchema`; seed updates must only fill missing artwork and must never replace an administrator-published manifest.
